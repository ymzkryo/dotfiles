# 編集者レビュー・プロンプト（共通）

`editorial-review` skill が各レビュアーへ渡すプロンプトの雛形です。
**媒体に依存する部分はすべてプレースホルダ**にしてあり、呼ぶ側（`blog-snail` など）が埋めます。

| プレースホルダ | 誰が埋めるか | 中身 |
| --- | --- | --- |
| `{{INTRO}}` | 呼ぶ側 | 役割と対象の宣言。1 文 |
| `{{MEDIUM}}` | 呼ぶ側 | この媒体・この文書種について（読者・文体・前提） |
| `{{REVIEWER_ROLE}}` | skill | レビュアーごとの編集者ロール |
| `{{CORE_MESSAGE}}` | 呼ぶ側 | 書く前に決めた想定読者と読後感（`core-message-writing` の成果） |
| `{{MEDIUM_CHECKS}}` | 呼ぶ側 | この媒体に固有の確認項目。無ければ「なし」 |
| `{{MEDIUM_OUTPUT}}` | 呼ぶ側 | 出力フォーマットに足す項目。無ければ空 |
| `{{DOCUMENT}}` | skill | 対象文書の全文 |

**置換するときの落とし穴は `SKILL.md` の「プロンプトを組み立てる」を読むこと。**
`---` で split する／`"{{" not in p` で未置換を見る、はどちらも壊れます。

{{CORE_MESSAGE}}

## レビューしてほしい観点
次の4つを軸に、**具体的に**指摘してください。抽象的な褒め言葉は要りません。

1. **構成**：話の順番・流れは自然か。導入で「何の記事か・誰の役に立つか」が伝わるか。見出しの粒度は適切か。冗長な段落・重複した説明はないか。逆に説明が飛んでいて読者が置いていかれる箇所はないか。締め（まとめ）が本文の主張と噛み合っているか。
   - **上の「この文書の狙い」で宣言した読後感に向けて、コアが冒頭から立っているか**を見てください。一番言いたいことが中盤以降に埋もれていたら指摘してください。
   - **見出しだけを上から順に読んだとき、記事全体のストーリーが伝わるか**を確認してください。「〜の工夫」「〜について」「〜の仕組み」のような中身が想像できない見出しがあれば、具体的な代案を出してください。
   - **想定読者がすでに知っている語に、括弧での言い換えや和訳が足されていないか**も見てください（例:「デプロイ（本番への反映）」）。コアをぼやかします。ただし括弧で具体値を足しているもの（「20分→8分」など）は対象外です。

2. **言い回し**：一文が長すぎて読みにくい箇所。回りくどい／曖昧な表現。媒体のトーン（丁寧＋柔らかめ）から浮いている硬すぎる or カジュアルすぎる表現。同じ語尾（〜です。〜です。）の連続。誤字・脱字・表記ゆれ。

3. **内容**：技術的に怪しい・言い切りすぎている箇所（事実確認が必要そうな主張）。読者が疑問に思いそうなのに説明されていない前提。タイトルと中身のズレ。読者にとっての「持ち帰り（で、結局どうすればいい？）」が明確か。公式ドキュメントへの参照が適切か・足りていないか。
   - **記事の記述と実装の現状が食い違っていないか**も見てください。記事が「まだ実装していない」「これからやる」と書いている機能が、実際にはリポジトリに存在することがあります（素材にした README が古いまま、というのが典型です）。参照できる範囲でリポジトリの実体を確認し、ずれていれば指摘してください。
   - バージョン依存の挙動を書いている箇所は、**どのバージョンで踏んだのか**が書かれているかを確認してください。書かれていないと、同じエラーで検索してきた読者が判断できません。
   - **記事が数字を主張の根拠にしている場合、その数え方が妥当かを確認してください。** 集計の対象期間に「そもそも動いていなかった期間」が混ざっていないか、grep の条件に関係ないものが引っかかっていないか、といった点です。数字ひとつで主張を支える構成は、そこが崩れると記事全体の信頼が落ちます。
   - **手元の材料から証明できる範囲を超えた結論になっていないか**を見てください。表や数字が示していることと、本文が言い切っていることがずれていることがあります（例:「接続先がある」ことは「必要である」ことの証明になりません）。反証が立つなら、その反証も挙げてください。
   - **一例からの過度な一般化**に注意してください。1 件の観測から「たいてい〜」「〜しやすい」と広げている箇所は、事実に沿った表現へ戻す提案をしてください。
   - **未着手・未確認のことを断定で書いていないか**も見てください。まだやっていない作業の結果を言い切っている箇所です。
   - **節の前後関係**を確認してください。「あとで触れる」「前述の」が実際の並び順と合っているか、という点です。

## 出力フォーマット
以下の形式で、**日本語**で返してください。忖度せず、辛口で構いません。ただし直せる形の提案にしてください。

- **総評**（2〜3文。この原稿の強みと、公開前に最優先で直すべき点）
- **指摘一覧**（重要度の高い順。各項目に以下を含める）
  - **重要度ラベル**（`[must]` / `[imo]` / `[nits]` のいずれか。**行頭に置いてください**）
  - 該当箇所（見出し名や引用で示す）
  - 種別（構成 / 言い回し / 内容）
  - 何が問題か（1〜2文）
  - どう直すか（具体的な代案。可能なら書き換え例）
{{MEDIUM_OUTPUT}}

### 重要度ラベルの付け方

**`[must]` は「このまま公開すると実害が出る」ものだけに付けてください。** 具体的には
次のどれかに当たるものです。

- **書かれていることが事実と違う**（数値・時系列・因果・バージョン・引用したコードや設定）
- **手元の材料から証明できない結論を言い切っている**
- **読者が手順どおりにやると失敗する**、または再現できない
- **機密が残っている**（顧客名・個人名・自宅や個人パス・生の認証情報）

`[imo]` は**直したほうが良いが公開はできる**もの（構成の入れ替え、言い回しの改善、
説明の厚みなど）。`[nits]` は**誤字・表記ゆれ・コードブロックの言語指定**など、
意味が変わらない範囲の指摘です。

**迷ったら `[imo]` に倒してください。** `[must]` の本数は改稿の進み具合を測る指標として
使うので、**「気になる」を `[must]` にすると指標が壊れます。** 逆に、上の 4 つに
当たるものを `[imo]` に落とすのも避けてください。
## 制約
- 対象文書の**ファイルは編集しないでください**。指摘（テキスト）を返すだけです。
- 機密チェックも兼ねてください：顧客名・個人名・自宅や個人パス・生の認証情報など、公開記事に載せるべきでない情報が残っていたら **最優先で** 指摘してください。
