# editorial-review ― 書いた文書を別の LLM に査読させる

**書いた本人（この Claude）だけで完結させないための工程です。** 自己添削では
自分の思い込みが残ります。`codex` / `agy` という**別の LLM に外部の目として**
査読させます。

**コードレビューではありません。** コードは `/self-review` が担当します。

## 呼ぶ側が渡すもの

この skill は**媒体に依存しません。** 次を呼ぶ側から受け取ります。

| | 中身 | 無いとき |
| --- | --- | --- |
| **対象文書のパス** | 査読する文書 | 必須 |
| **`{{INTRO}}`** | 役割と対象の宣言。1 文 | 必須 |
| **`{{MEDIUM}}`** | この媒体・文書種について（読者・文体・前提） | 必須 |
| **`{{CORE_MESSAGE}}`** | 書く前に決めた想定読者と読後感 | `core-message-writing` の成果を渡す。無ければ「未設定」と書く |
| **`{{MEDIUM_CHECKS}}`** | この媒体に固有の確認項目 | 「なし」 |
| **`{{MEDIUM_OUTPUT}}`** | 出力フォーマットに足す項目 | 空 |
| **第 1 段階の対応表のパス** | 「主張 → 一次情報」の対応表 | 無ければその旨を伝えて続行 |

**プロンプトの雛形は `references/review-prompt.md`。**

## レビュアー

| レビュアー | 割り当てロール（`{{REVIEWER_ROLE}}`） | 起動方法の単一の出所 |
|---|---|---|
| `claude`（別インスタンス） | 書籍の編集者（構成・内容の深さ重視） | `claude -p` |
| `codex` | 校閲担当（事実確認・表記ゆれ・機密漏れ重視） | `~/.claude/skills/codex` |
| `agy`（Antigravity） | 校閲担当（事実確認・表記ゆれ・機密漏れ重視） | `~/.claude/skills/agy` |
| `copilot` | 技術雑誌の編集者（言い回し・読みやすさ重視） | `~/.claude/agents/copilot-reviewer.md` |

**4者そろえるのが基本だが、動くものから使えばよい。**
**各レビュアーに少し違うロールを割り当てて視点を散らす。**

**2026-10-10 に `copilot` が使えることを確認した。**
それまで「未インストール」と書いて `agy` に 2 枠を兼ねさせていたが、**誤りだった**
（`command -v copilot` → 1.0.95 / global npm に `@github/copilot`）。
**`gh copilot`（gh 拡張）とは別物**で、入っているのは standalone のエージェント型 CLI。

**役割の実績（2026-09 の3記事）。** `claude` と `codex` が事実誤り・論理の飛躍をよく拾う。
`agy` は事実誤りをほぼ出さず、構成・文体と house style の抜けを拾う。
**`agy` の「内容」指摘は誤読が混ざる**ので、実物に当たってから採ること。

**ただしこの実績は 2026-10-10 の実測と食い違った。** `[must]` の定義を
プロンプトに足した後に測ると、`agy` の `[must]` 3 件は**全部が事実・機密・論理**だった。
**ラベルの定義がレビュアーを事実側へ誘導した可能性がある。**
標本はどちらも小さい（実績 3 記事 / 実測 1 記事）ので、**どちらかに寄せて
レビュアーを減らす判断はまだしない。**

## 手順

### 1. プロンプトを組み立てる

レビュアーごとに `references/review-prompt.md` のプレースホルダを差し替え、
スクラッチパッドに一時ファイルとして書き出す。**本文はインラインで埋める**
（パス依存を避ける）。

**2 回踏んだ落とし穴がある。**

- **テンプレートを `---` で split しない。** 対象文書の frontmatter にも `---` が
  あるため、区切りを見誤って**指示文が丸ごと落ちる**。落ちても実行自体は成功し、
  「文書だけ渡して査読を頼んでいない」状態になる。
  `tmpl.index("---\n\n{{INTRO}}")` のように**指示文の開始位置から末尾まで**を取る
- **未置換チェックに `"{{" not in p` を使わない。** Hugo のショートコード
  `{{< ref "..." >}}` のように、**対象文書の中に `{{` があることがある**。
  `{{INTRO}}` `{{MEDIUM}}` `{{REVIEWER_ROLE}}` `{{CORE_MESSAGE}}`
  `{{MEDIUM_CHECKS}}` `{{MEDIUM_OUTPUT}}` `{{DOCUMENT}}` と
  **プレースホルダ名で 1 つずつ確かめる**

生成したら、投げる前に**指示文が入っているか目視する**のが確実。

### 2. 並列で実行する

```bash
# 例（スクラッチパッドの $DIR にプロンプトを用意済みとする）
claude  -p "$(cat "$DIR/prompt-claude.txt")" < /dev/null         > "$DIR/out-claude.md"  2>&1
agy     -p "$(cat "$DIR/prompt-agy.txt")" --sandbox --print-timeout 15m \
                                                                 > "$DIR/out-agy.md"     2>&1
codex   exec -s read-only --skip-git-repo-check -C "$DIR" \
        -o "$DIR/out-codex.md" - < "$DIR/prompt-codex.txt"        > "$DIR/log-codex.txt"  2>&1
copilot -s --no-ask-user --allow-all-tools \
        --deny-tool='write' --deny-tool='shell(rm)' --deny-tool='shell(git:*)' \
        < "$DIR/prompt-copilot.txt"                               > "$DIR/out-copilot.md" 2>&1
```

**渡し方が 4 者で 3 通りに分かれている。取り違えると中身が届かない。**

| | 渡し方 |
| --- | --- |
| `claude` / `agy` | **引数**（`-p "$(cat ...)"`）。**`claude` は `< /dev/null` で stdin を塞ぐ** |
| `codex` | **標準入力**（`exec ... -` の `-` が stdin を指す） |
| **`copilot`** | **標準入力。`-p` を付けてはいけない**（付けると stdin が無視される） |

**`copilot` の落とし穴は `~/.claude/agents/copilot-reviewer.md` が単一の出所。**
`--allow-all-tools` が非対話モードで必須、`--no-ask-user` が無いと質問して止まる、
`-s` が無いと stats が混ざる。

**`claude -p` にも `< /dev/null` が要る。** 付けないと
`Warning: no stdin data received in 3s, proceeding without it.` が
**出力ファイルの先頭に混ざる**。3 秒待ってから続行するのでレビュー自体は成功し、
**壊れていることに気づきにくい**。

**`codex` は `-o` で査読本文だけを別ファイルに書かせる。** `-o` なしで stdout を
リダイレクトすると、バージョン・workdir・推論トレースを含む **262 KB** が入る
（`-o` ありは査読本文のみの 12.8 KB）。指摘を数えるときにトレースのノイズを拾う。

**所要時間は 1 分〜4 分**（2026-10-10 実測、25,836 バイトの文書で
`agy` 62 秒 / `codex` 210 秒 / `claude` 240 秒）。**前景で待つと 2 分で打ち切られる**ので、
バックグラウンド実行にして完了通知を待つ。

### 3. 指摘を統合する

**同じ指摘は束ね、対立する指摘は自分で判断する。** 全指摘を鵜呑みにしない。
レビュアーが的外れなこともある。

**数えるのは目視ではなく `scripts/compare_reviews.py` でやる。**

```sh
# その周のラベルを数える
python3 scripts/compare_reviews.py count "$DIR"/out-*.md
# 前の周から [must] が落ちていないかを見る
python3 scripts/compare_reviews.py diff "$PREV_DIR" "$DIR"
```

**ラベルの装飾がレビュアーごとに違うため、手で数えると取りこぼす。** 実測では
`claude` が `- **[must]**`、`codex` が `- [must]`、`agy` が `` #### `[must]` `` だった。
行頭の `-` `*` `#` `` ` `` `>` を剥がさないと **`agy` が 0 件に見える**。
最初に書いたスクリプトが実際にそうなっていた。

### 4. 反映する前に、指摘そのものの裏を取る

**`references/primary-sources-checklist.md` を指摘に当てる。**
レビュアーが返すのは仮説のことがある。詳細はあちらが単一の出所。

### 5. 反映したら通し読みして、もう一周投げる

**レビューは1周で終わらせない。** 2026-09 の実績では 2周目・3周目でも毎回 `[must]` が出た。

| 文書 | 周回 | 出た事実誤り |
|---|---|---|
| 2026-09-22 | 4周。3周目まで毎回 `[must]` | 計 8 件 |
| 2026-09-23 | 2周目でも `[must]` 7 件 | 計 9 件 |
| 2026-09-29 | 6周 | 計 24 件 |

**止めどきは「一次情報チェックリストを全項目当てたとき」。**
**「新規の指摘が出なくなった」で止めてはいけない。** 2026-09-29 の記事は
**3周目まで新規の事実誤りがゼロで、4周目に検証範囲を広げたら 6 件出た**。
**出ないことと見ていないことは区別が付かない。** 周回数も先に決めない。

**反映したら差分ではなく通し読みを 1 回入れる。** 反映作業そのものが新しい矛盾を生む。
詳細は `references/primary-sources-checklist.md`。

## フォールトトレランス

- いずれかの CLI が失敗（非ゼロ終了・エラー出力）しても**全体を止めない**。
  そのレビュアーだけスキップし、「◯◯はスキップ（理由）」と記録して残りで続行する
- **終了コードだけで成功を判断しない。出力が空でないことを必ず確かめる。**
  2026-10-10 に `claude -p` が **`exit=0` で 186 秒走ったのに出力 0 バイト**という
  形で失敗した。同じプロンプトを再実行したら通ったので一時的なもの。
  **終了コードは成功を示していた**ので、`[ -s "$out" ]` を見ないと
  「レビューを取れた」と誤認して次の周に進んでしまう

```sh
for r in claude codex agy; do
  [ -s "$DIR/out-$r.md" ] || echo "$r はスキップ（出力が空）"
done
```
- **既知**: CLI の引数は版によって変わる。落ちたらまず `<cli> --help` で現行の引数を確認する
  （2026-09-11 に `codex` の `-a` 廃止でスキップが発生した）
- **一時的な失敗は 1 回だけリトライしてからスキップする。** `agy` は 503 を返すことがあり、
  2026-09-29 の記事では 1・2・5 周目が全滅した。ただし 2026-10-10 に測ったときは
  3者とも一発で通った（`agy` 62 秒・503 は 0 件）ので、**恒常的に不調と決めつけない**
- 最低1者のレビューが取れれば反映に進む。**全滅した場合のみ**ユーザーに知らせて指示を仰ぐ
- レビュアーはあくまで**別の LLM**を使うのが目的（外部の目）。
  **この Claude 自身の自己添削で代替しない**

## 書くときに繰り返し出た指摘

**レビューで何度も同じことを言われた型。** 書く段階で避けられる。

### 証明できる範囲を超えて書かない

**手元の材料から言えることと、言いたいことを混ぜない。**

- 「接続先がある」と「必要である」は別。表が示すのは前者だけ
- 一例から「たいてい〜」と一般化しない。**今回はこうだった**に留める
- 未着手のことを断定で書かない（「また増えるだけです」→「また増えそうです」）
- 反証が立つなら、**反証自体を本文に書く**。潰せないなら結論を弱める。
  そのほうが文書は強くなる

### 素材が古いことがある

レビューで最も価値があったのは、**文書の記述と実装の現状が食い違っている**という指摘だった。

2026-09-09 に「この機能はこれから実装する」と書いたが、実際にはすでに実装済みだった。
素材にした README の「現在の制約」節が更新されずに残っていて、それを信じたため。
**同じファイルの中で情報が食い違っていた。**

- README や memo の記述を鵜呑みにせず、**`git log` で直近のコミットを見る**
- 「まだ〜していない」「これから〜する」と書くときは、**実物の有無を実際に確かめる**
- 素材が別セッションで並行して動いている場合は特に注意する

### 素材そのものが消えていることがある

2026-09-23 では、元ネタの一行が**ファイルから消えていた**（ツールが置換した）。
**`git log` / `git show` で原文を復元する。** このときは復元した原文が文書の芯になった。

### 前提を本人に確認すると、結論が覆ることがある

2026-09-23 の記事は、**書き上げてレビューまで通したあとに結論が反転した**。
実際の使い分けを聞き取ったら誤診だった。

- **本人しか知らない事実**（台数・構成・使い分け・経緯）は、骨格を決めるなら先に聞く
- 聞かずに書けることと書けないことを切り分け、**書けない部分は推測で埋めない**
- 型番や仕様が分かったら**公式ドキュメントで確認する**

### 文書の外の食い違いも拾う

レビューは文書だけでなく**リポジトリのコメントや実装との食い違い**を拾う。
文書側で慎重に限定した主張を、コード側のコメントが言い切ったまま放置していることがある。

2026-09-22 の記事では、これが3本の PR になった。

**文書に「ここは弱い」と書いたなら、実装を直すかどうかまで考える。**
ただし文書の PR には混ぜず、別 PR に分ける。

## いまの制約

- **プロンプトの汎用部分に「記事」という語が 5 箇所残っている。**
  `blog-snail` から切り出した時点のままで、**2 つめの呼ぶ側（設計書）を作るときに
  一般化する**。一例から一般化しないため、いまは触っていない
- **段階分離（事実 → 構成 → 文体）はまだ入っていない。**
  切り出しを挙動を変えずにやるため、別の変更として分けた

## やらないこと

- **コードのレビュー**（`/self-review` の担当）
- **この Claude 自身の自己添削で外部レビュアーを代替すること**
- **レビュー指摘の無批判な全反映**（おかしい指摘は理由を添えて見送る）
- **対象文書のファイルをレビュアーに編集させること**（指摘のテキストだけ返させる）
